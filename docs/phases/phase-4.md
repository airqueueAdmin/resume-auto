# Phase 4 - RAG and Matching

## Status

Complete for the initial synchronous, local-provider scope.

## Objective and scope

Use a Job Description to retrieve relevant user-owned Experience and Project evidence, pass that
bounded context to an LLM, and return matching analysis with validated source references and
citations.

## Design reasons and important decisions

- The saved JobPosting remains the source of truth and is loaded through the existing ownership-aware
  service. The client cannot provide an authoritative user ID or arbitrary job text for this flow.
- Retrieval runs before generation. The LLM sees only the authenticated user's active, top-ranked
  Phase 3 chunks selected for the Job Description.
- Citation labels are generated by the server and resolved after the LLM response. This avoids
  trusting model-generated UUIDs or source IDs.
- The server rejects a citation absent from the retrieved context and rejects strengths or
  recommendations that have no citation. This turns provenance into an enforceable application rule.
- Resolved source snapshots are stored in the immutable `ai_job_matches` JSONB artifact so later
  source edits or re-indexing do not erase what supported the result at generation time.
- The request is synchronous and uses the same timeout/retry/provider boundary as Phase 2. Queueing or
  streaming is deferred until latency measurements justify it.

## Implemented features

- `POST /api/v1/ai/match-job`
- Local Ollama and optional OpenAI structured matching adapters
- `job-match-v1` system prompt with untrusted-data and prompt-injection guidance
- Bounded retrieval context with server-assigned citation labels
- Source citation resolution and validation
- Immutable `ai_job_matches` persistence with provider metadata, prompt version, usage, and source
  snapshots
- Ownership, no-evidence, and provider/error handling
- README, OpenAPI, migration, step record, and ADR documentation

## Explicitly excluded features

- Resume generation and approval workflow
- Writing generated content into ResumeVersion
- Tool calling, agents, evaluation datasets, asynchronous jobs, and production hardening
- Claim-level factual verification beyond checking that cited source evidence was retrieved

## Tests and executable verification

- Full Maven suite: 40 tests passed, 0 failures, 0 errors.
- Flyway applied all 7 migrations in PostgreSQL Testcontainers.
- Hibernate validated the new `ai_job_matches` JSONB entity.
- Integration tests verified cross-user matching returns 404 and no indexed evidence returns 422
  `RAG_CONTEXT_EMPTY`.
- Unit tests verified provider structured matching and citation mapping/rejection.
- Automated tests use local HTTP/provider stubs and do not call a paid provider or persist a real
  model-generated match; local application startup and OpenAPI exposure were verified separately.

## Failures encountered and root causes

- The first Phase 4 test run expected the Phase 3 six-migration schema. V7 correctly increased the
  migration count to seven; the test assertion and table count were updated, then the complete suite
  passed.
- The first matching adapter design reused the analysis prompt-version accessor, which would have
  recorded `job-analysis-v1` for RAG results. A separate `matchingPromptVersion()` boundary was added
  so artifact metadata records `job-match-v1` correctly.

## Concepts the learner must understand

- RAG is a retrieval-plus-generation flow; retrieval context limits what the model can inspect but
  does not guarantee factual correctness.
- Citation validation must happen on the server after generation, not only in the prompt.
- Source snapshots and derived embeddings serve different audit purposes: the vector helps find a
  source, while the snapshot records what evidence was used.
- Context and Top-K bounds are latency and cost controls as well as prompt-quality controls.

## Completion criteria

- [x] Job Description retrieval context is passed to a structured LLM request.
- [x] Output contains matching findings and source labels.
- [x] Labels are resolved only against retrieved, user-owned chunks.
- [x] Invalid and uncited grounded findings are rejected.
- [x] Valid results are stored as immutable artifacts with source snapshots.
- [x] Ownership, empty-context, provider, migration, and unit tests pass.
- [x] Resume generation and mutation remain excluded until Phase 5.

## Next phase and known limitations

Phase 5 will generate resume drafts from existing source facts and require user approval before a new
ResumeVersion is created. Phase 4 currently uses one chunk per source and synchronous full-user
re-indexing; retrieval quality and latency should be measured before introducing chunk refinements or
asynchronous processing.
